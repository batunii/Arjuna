# Distractor Reel — Block A Tablet Stimulus

Implements the tablet content described in `Dissertation/testing-strategy-v2.md` §4.1
(Block A, workstation focus task) and §10.1 (determinism): the two tablets at ±35°
azimuth show either a static black screen (Distractors-absent) or a fast-cut,
high-motion, bright reel with scheduled salient event bursts (Distractors-present).

This is a standalone, self-contained web page — **not** part of the Unity/Quest build.
It runs in any tablet's browser, offline, with no install step.

## Why a web page and not a native app

The tablets are separate physical devices from the Quest headset (§10.1: "distractor
tablets are manual by design"). A browser page requires no build/signing pipeline,
can be tuned and reloaded in seconds, and is trivial to run identically on any
Android/iOS tablet.

## Files

| File | Role |
|---|---|
| `distractor-reel.html` | The player. Self-contained (no external requests once loaded). |
| `distractor_schedule.js` | Generated burst schedule, loaded by the player via `<script src>`. |

`distractor_schedule.js` is generated by `Tools/make_distractor_schedule.py` (do not
hand-edit) — it's the checked-in, versioned schedule required by §10.1's "no
improvised stimuli" rule. A record copy of the same data also lands at
`Assets/StreamingAssets/StudySchedules/distractor_reel.json` alongside the Block B
probe schedules.

Regenerate after tuning burst timing/count:
```
python Tools/make_distractor_schedule.py
```

## How the ambient reel is deterministic without a schedule file

Only the **bursts** (the spec's "scheduled salient event bursts... at fixed
timestamps") come from the checked-in JSON/JS. The continuous fast-cut/high-motion
background between bursts is a pure function of elapsed playback time (hashed cut
index + closed-form motion paths) — no `Math.random()` at runtime — so it is already
bit-for-bit identical on every load and every device without needing its own schedule
file.

## Device robustness (why these exist)

- **Screen Wake Lock** requested on Start, re-requested on `visibilitychange`.
  Without it, Android can screen-sleep mid-condition — a real risk for the
  static-black condition, which is otherwise 3.5 min of zero touch input and
  zero screen change. Best-effort (older WebViews without the API just fall
  back to whatever the device's own screen-timeout setting is — worth checking
  that setting is generous on the actual study tablets as a backstop).
- **Fullscreen requested on Start** to hide the browser chrome/address bar
  automatically instead of relying on manual kiosk-mode setup per tablet.
- **`touch-action: none` / `oncontextmenu` disabled / `-webkit-touch-callout: none`**
  so the long-press reset gesture (and general handling) can't be hijacked by
  the browser's native text-selection callout or context menu.

## Running it on the tablets

1. Copy `distractor-reel.html` and `distractor_schedule.js` to each tablet (same
   folder), e.g. via USB, `adb push`, or a shared drive. Both files must sit together.
2. Open `distractor-reel.html` directly in the tablet's browser (Chrome recommended).
   No web server needed — it works from a local file.
3. Put the browser in fullscreen/kiosk mode if the browser chrome would be visible
   to the participant.
4. Before each condition: tap **Distractors-absent** or **Distractors-present** to
   match the current condition, then tap **START** on the experimenter's spoken
   countdown ("3-2-1-play"), per the existing protocol in
   `Assets/PassthroughCameraApiSamples/ShaderSample/Scripts/Study/README.md`
   ("tablets: START REEL" cue printed by `ConditionSequencer`).
5. To reset for the next condition: press-and-hold the bottom-right corner
   (~1 s) — this returns to the mode-select screen. (A deliberate long-press,
   not a tap, so it can't be triggered by accident.)
6. The reel is 210 s (3.5 min), matching a Block A condition; it loops
   automatically if a condition overruns.

## Photosensitivity note

Each burst fires at most 2 brief flash pulses within its 0.6 s window (~130 ms and
~95 ms, separated by a gap) — well under the general "no more than 3 flashes in any
1-second period" threshold, and bursts themselves are 20-30 s apart, not a sustained
strobe train. Worth a line in the ethics-amendment conversation (testing-strategy-v2
§11) alongside the other ethics-delta items, but the design is already conservative.

## Verifying a change

There's no test harness checked in (this is a two-file static page). To sanity-check
after an edit, open the file in a desktop browser and manually step through both
modes; the on-screen `t=` readout in REEL mode makes it easy to confirm bursts land
at the timestamps printed by `make_distractor_schedule.py`.
