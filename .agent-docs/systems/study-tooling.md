# System: Study Tooling

Last updated: 2026-07-14

Everything under `Assets/PassthroughCameraApiSamples/ShaderSample/Scripts/Study/`. Two distinct
layers share this folder — **do not conflate them**:

1. **Formal study infrastructure** — drives the actual MSc dissertation data-collection sessions
   (`Dissertation/testing-strategy-v2.md` §13). Contract-bound CSV schema, Latin-square
   counterbalancing, experimenter-keyboard-driven.
2. **Informal test harness** (`TestModeSequencer` + `BlobTargetController`, added on branch
   `Test/FinalCountDown`/`Test/TestBlobs`) — a quick-iteration preview tool for demoing/tuning
   vignette modes. Deliberately **standalone** from layer 1: no shared logger, no scene wiring,
   self-bootstraps. Do not wire it into `ConditionSequencer` or `StudyLogger`.

Both layers drive the vignette managers exclusively through
[`IStudyVignetteControl`](<../systems/focus-vignette.md>), implemented by both
`CameraSphereVignetteManager` and `VideoTestSceneManager` — so neither layer needs to know which
scene it's running in.

---

## Layer 1 — Formal study infrastructure

| Script | Role |
|---|---|
| `StudyLogger.cs` | Per-frame CSV heartbeat + labelled events, flushed every frame. Output: `persistentDataPath/study_P<pid>_<timestamp>.csv`. Schema is contracted with `Tools/validate_session.py` — **never change columns/labels without updating both.** |
| `ConditionSequencer.cs` | Latin-square condition orders derived from participant ID, condition state machine, configuration guards, experimenter controls (keyboard, arrives via `UnityEngine.Input` — adb keyevents). |
| `ProbeScheduler.cs` | Block B diamond probes from versioned JSON schedules (`Assets/StreamingAssets/StudySchedules/probes_B1.json` / `B2.json`, generated by `Tools/make_probe_schedule.py`). ISO 17488 response window (100–2500 ms), head-yaw deferral. |
| `CPTPanel.cs` | Block A Option V world-locked Go/No-go panel (runtime-generated shapes). |
| `ClickProbeTest.cs` | Standalone click-capture harness — left controller aims a cyan reticle, left trigger logs a `CLICK` event (video time + az/el) for offline matching against the bake. `m_autoOpenSession` opens its own StudyLogger session (pid 999); turn off when folding into the real flow. |
| `SceneSwitcher.cs` | Hold left `Y` (~1 s) or key `V` (adb) to `SceneManager.LoadScene` between `CameraSphereVignette` and `VideoTestScene` — a **full scene reload**, not in-place (the two scenes own different pipelines: live PCA cameras vs. `VideoPlayer`). Shows a hold-progress ring (`SelectionLine`). |
| `SwitchFeedbackController.cs` | `DontDestroyOnLoad` bootstrap (`RuntimeInitializeOnLoadMethod`) — shows a "SWITCHED / PASSTHROUGH" or "SWITCHED / VIDEO" toast for 2.8 s after any scene load. |
| `IStudyVignetteControl.cs` | Shared study API — see [focus-vignette.md](<../systems/focus-vignette.md>#study-api-istudyvignettecontrol). |

**Session runbook, experimenter keybindings, and CSV pull/validate steps:** see
`Assets/PassthroughCameraApiSamples/ShaderSample/Scripts/Study/README.md` (kept current for the
actual protocol — this doc doesn't duplicate it).

**Scene wiring:** both scenes have a `StudyRig` GameObject (created via the `Meta > Study > Wire
VideoTestScene` / `Wire CameraSphereVignette` / `Wire Both Scenes` Editor menu items in
`Assets/Editor/SetupStudyRig.cs`, not by hand) holding `StudyLogger` + `ConditionSequencer` +
either `ProbeScheduler`+`ClickProbeTest` (video scene) or `CPTPanel` (passthrough scene).

## Layer 2 — Informal test harness (branch `Test/FinalCountDown` → `Test/TestBlobs`)

### TestModeSequencer.cs

A 4-mode preview loop, entirely separate from `ConditionSequencer`. **Self-bootstraps** via
`[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]` — no scene wiring, no menu step, just Play/build.

Default sequence (edit the `m_modes` list in the Inspector to reorder/change):

1. SignPop + Video (`VideoTestScene`)
2. No Filter + Video (`VideoTestScene`, same clip)
3. Hard Dark + Passthrough (`CameraSphereVignette`)
4. No Filter + Passthrough (`CameraSphereVignette`)

...then **loops back to mode 1** (`m_index = (m_index + 1) % m_modes.Count`) — no terminal "done"
state.

Controls (Quest controller only, no keyboard fallback):
- **X** — toggle. Video modes: play/pause the clip (`VideoTestSceneManager.SetVideoPlaying`).
  Passthrough modes: start the gradual vignette-forming coroutine, or reset it to 0
  (`IStudyVignetteControl.StudySetActive`). First press also dismisses the instructions text.
- **A** — advance to the next mode (leaves the current mode stopped/reset first via `ApplyActive(false)`).

Moving between a video mode and a passthrough mode triggers a full `SceneManager.LoadScene` (same
reasoning as `SceneSwitcher`). A world-space instruction UI (parented under the persistent
`DontDestroyOnLoad` GameObject so it survives every scene load) shows `"{index}/{count}  {label}"`
+ a "Press [X] to start" hint. Uses `renderQueue = 4100` on its Canvas material — same trick as
the mode toast — so it draws over the head-centred vignette sphere (`queue 3000`) instead of being
occluded.

**Does NOT set `StudyInputLock`** — deliberately, so the manager's own free-play A/B/trigger
controls stay live. (An earlier version did lock input; this took away right-controller free-play
for no functional reason and was reverted.)

**Locks a fixed windscreen focus window on video-mode entry** (`m_lockVideoWindow`, default on,
±25° az / ±15° el around video-forward — added 2026-07-18, tightened same day from ±40°/±25°): without it nothing is ever painted in
the harness, so SignPop fell back to gaze auto-follow and the person gate ran against wherever
the participant looked — an uncontrolled variable in the mode-1-vs-2 comparison. The same window
is set in the no-filter mode (invisible there), so geometry and procedure are identical in both
arms. Re-applied on every video-mode entry, so a free-play repaint only lasts until the next mode
switch.

**Note:** `entry.noFilter = true` means "no filter" — `StudySetActive` is skipped for that entry
regardless of its `vignetteMode` value (the mode value is irrelevant when suppressed via
`StudyEffectSuppressed`, see below).

### BlobTargetController.cs

Sibling component on the same persistent GameObject as `TestModeSequencer` (added via
`gameObject.AddComponent<BlobTargetController>()` in `TestModeSequencer.Awake()`). Active only
during modes 1 & 2 (any `TestStage.VideoScene` mode); inert during modes 3 & 4.

**What it does:** places low-salience, deliberately camouflaged clickable "blob" targets at real
traffic-light/stop-sign locations from the baked detection track, for testing whether a DR filter
(SignPop, mode 1) helps you notice/click them faster than no filter (mode 2).

**Selection** (`EnsureGenerated`, runs once per app session, reused for every mode 1/2 activation
and every video loop — same random set both times, for a fair paired comparison):
1. `VideoTestSceneManager.BuildDetectionLifetimes({9, 11}, holdSeconds)` reconstructs every real
   object's full on-screen lifetime by walking the whole baked track once (same identity heuristic
   as the live tracker: same class, nearest centre within a size-scaled radius) — see
   [video-test-scene.md](<video-test-scene.md>#detection-lifetime-reconstruction).
2. Filter: lifetime ≥ `m_minLifetimeSec` (0.75s default — excludes unclickable single-sample
   blips) AND angular eccentricity from video-forward ≥ `m_minEccentricityDeg` (20° default —
   keeps selection **peripheral**, out of the cone a driver naturally fixates on).
3. Seeded random pick (`m_seed`) of `m_targetCount` (10 default) non-overlapping windows
   (`m_minGapSec` buffer between any two), guaranteeing at least `ceil(count * m_longFraction)`
   (5 of 10 default) have a real lifetime > `m_longLifetimeSec` (2s default).
   - These defaults were checked against the actual current bake, not guessed: ~9% of all
     reconstructed tracks exceed 2s: real candidate pools were 107 (any eccentricity) / 97
     (≥20°) / 52 with lifetime >2s at ≥20° — comfortably enough headroom for 10 targets.

**Per-frame:** tracks a single pointer (`m_ptr`) into the sorted-by-`tStart` target list (video
time is ~monotonic; a large backward jump = video loop, resets `m_ptr` and all `resolved` flags
for a fresh pass). The current target's box position is bracket-lerped between its two straddling
samples exactly like `VideoTestSceneManager.UpdateBakedDetections` does, converted via the public
`DetectionBoxToAzElRect` wrapper — so a blob lines up exactly with "where the box would have
been."

**Input & hit test:** left controller aims a cyan reticle (`ClickProbeTest`'s exact convention);
left trigger (`OVRInput.RawButton.LIndexTrigger`) checks angular distance to the target's current
direction — within `m_hitAngleToleranceDeg` (10°) while visible, or within
`m_hitGraceSec` (0.75s) after it disappears (aimed at its *last known* position — the object is
hidden during this grace tail, not frozen visibly in place). A miss (window + grace elapses with
no correctly-aimed press) or a bad-aim press (pressed, target active, angle too wide) are both
logged; a bad-aim press does not end the trial — retries are allowed until the window closes.

**Hit feedback:** blob flashes bright green (`m_hitFlashColor`), scales up `m_hitFlashScale`
(1.6×) for `m_hitFlashSeconds` (0.25s), plus a short synthesized beep (`AudioClip.Create` —
no audio asset needed) via an `AudioSource` on the controller's own always-active GameObject
(not `m_blobGO`, which toggles active/inactive constantly and would silently drop
`PlayOneShot`). The main per-frame show/hide logic explicitly yields to the flash coroutine
(`if (m_flashCoroutine == null) { ...ShowBlob/HideBlob... }`) — otherwise the just-hit target,
which stays "current" until its window naturally closes, would immediately stomp the flash's
scale/visibility.

**Visuals:** small (`m_blobSizeDeg` 1.0° default), translucent (`m_blobColor` alpha 0.5),
muted-olive tone `(0.40, 0.38, 0.30)` — tuned down from an initial too-large/too-opaque pass.
Needs `m_markerMaterialTemplate` assigned (reuse `SelectionDotMat`) for Android builds — the
editor-only `Shader.Find("Standard")` fallback is explicitly switched to Fade blend mode so alpha
still renders correctly during quick in-editor iteration.

**Logging:** own CSV (`persistentDataPath/blobtargets_<timestamp>.csv`), deliberately **not**
`StudyLogger` (same reasoning as everywhere else in this layer — must not touch the real study's
contracted schema). Columns: `t_ms,mode,target_id,t_start,t_end,duration_s,outcome,rt_s,angle_deg`.
Outcomes: `hit`, `miss`, `bad_aim_attempt`, `false_alarm`.

### Setup requirement

Assign `m_markerMaterialTemplate` on `BlobTargetController` (reuse `SelectionDotMat.mat`) before
building for device — otherwise it warns and falls back to `Shader.Find("Standard")`, which
breaks on Android's stripped shaders.

### Bugs fixed while building this (apply beyond the test branch)

- `UpdateDetectionUniforms()` in **both** `VideoTestSceneManager.cs` and
  `CameraSphereVignetteManager.cs` now zeroes `_DetectionCount` when `StudyEffectSuppressed` is
  true. The shader's detection-highlight boost (`CameraSphereVignette.shader:683-690`) ran
  independently of `_VignetteStrength`, so a "no filter"/baseline condition — including in the
  **real study** — could still visibly highlight detected lights/signs, contradicting
  `StudyEffectSuppressed`'s documented contract ("effect forced invisible... without changing
  anything else the participant experiences").
- Added `IStudyVignetteControl.StudySetActive(bool)` (implemented in both managers) so an "on"
  state can ramp in via the existing gradual-formation coroutine instead of `StudySetMode`'s
  instant snap-to-full-strength, and an "off" state can reset without touching mode/window. See
  [focus-vignette.md](<../systems/focus-vignette.md>#study-api-istudyvignettecontrol).
